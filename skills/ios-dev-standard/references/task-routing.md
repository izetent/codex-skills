# 任务分流与执行策略

## 目录

- 任务类型判断
- 功能开发流程
- Bug 修复流程
- 架构调整流程
- UI/适配任务流程
- Review 流程

## 任务类型判断

先判断任务属于哪类：

```text
新项目架子
新增功能
Bug 修复
页面拆分
架构调整
UI 设计还原
自适应布局
网络/缓存/存储/鉴权
并发/生命周期/性能
测试补充
代码审查
```

再判断责任层：

```text
App 壳层
Feature 页面层
Domain 业务层
Data 数据实现层
Session 共享状态层
Core 基础能力层
Shared UI 层
Resources/Configs 配置资源层
Tests/Tools 质量工具层
```

## 功能开发流程

1. 明确用户路径和成功标准。
2. 判断是否需要新页面、新接口、新状态源、新组件。
3. 定义 Feature 落点。
4. 定义 `ViewState`、`ViewAction`、`ViewEvent`。
5. 如有业务规则，先补 UseCase 和 Repository 协议。
6. 如有接口，补 DTO、Remote、Mapper、Repository 实现。
7. 如影响登录态、用户态、会员态或全局配置，补 Session。
8. UI 只绑定 ViewModel，不直接访问数据实现。
9. 复用 Shared 和 DesignSystem。
10. 补风险对应测试。

## Bug 修复流程

1. 复述现象、触发条件、期望结果、实际结果。
2. 定位是否属于：
   - 状态归属
   - 一次性事件
   - 导航 contract
   - 生命周期
   - 并发竞态
   - 网络/缓存/存储
   - 布局适配
   - 设计系统
   - 可访问性
3. 读取相关实现和调用链。
4. 找到证据后再改。
5. 修改真正负责问题的层。
6. 验证原始路径和邻近路径。

禁止：

- 未复现或未定位就直接改。
- 用延时、重试、强刷掩盖问题。
- 为修一个表现改多个无关层。

## 架构调整流程

适用场景：

- 页面过厚。
- 共享状态多处维护。
- 网络或存储散落。
- 组件复制严重。
- Feature 互相依赖。

执行：

1. 先画出现有依赖方向。
2. 明确目标依赖方向。
3. 先抽协议和边界，再迁移实现。
4. 分批提交小步调整。
5. 每步都保持可编译。

## UI/适配任务流程

1. 确认设计意图：信息层级、交互优先级、视觉节奏。
2. 找到现有 token 和组件。
3. 优先复用，不复制样式。
4. 检查小屏、大屏、iPad、横屏。
5. 检查 Dynamic Type、暗黑模式、长文案、键盘、VoiceOver。
6. 对视觉敏感页面补截图验证或明确人工检查项。

## Review 流程

按严重程度输出：

1. 崩溃、数据错误、安全问题。
2. 生命周期、并发、状态重复、重复事件。
3. 架构边界和依赖方向。
4. UI 适配、设计系统、可访问性。
5. 测试缺口和可维护性。

Review 不以代码风格为主，除非风格问题会造成维护风险。
