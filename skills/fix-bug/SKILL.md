# 缺陷修复

当任务是修复任何框架、平台、服务或共享代码路径中的缺陷时使用本技能。修复必须以证据为基础，像手术刀一样精准：找到真实责任层，只修改真正导致问题的代码，并保护既有业务行为。

## 核心规则

- 未描述现象、触发条件、影响范围、复现路径前，不直接改代码。
- 区分根因和表象；不能用兜底分支、延时、强刷、重试掩盖根因。
- 证据不足时先排查，必要时在最窄位置加临时日志或链路追踪。
- 不替用户做错误假设；发现矛盾、歧义或证据不足时，先停下来说明。
- 先判断问题归属层：界面、状态、生命周期、缓存、网络、权限、协议、存储、异步、平台能力或共享模块。
- 修复必须像手术刀一样精准，只改真正导致问题的层和代码。
- 多个修复方案都有合理性且存在取舍时，先给方案和推荐项。
- 根因明确且修复边界小，直接做最小修改。
- 修完必须验证原始问题和相邻回归路径，不能只看当前页面或当前输入。

检验：每一行修复都必须能对应到一个已确认的根因或验证需要；如果只是“顺手优化”，不要放进本次修复。

## Karpathy 启发的执行原则

- 编码前思考：先暴露假设、困惑和取舍，不把不确定性藏进修复。
- 简洁优先：用最小修复解决根因，不堆抽象、不扩接口、不写臃肿兜底。
- 精准修改：只碰当前缺陷必须触碰的代码，不改自己不理解的无关代码或注释。
- 目标驱动：优先定义复现路径、验证方式和成功标准，再循环排查到闭环。

检验：如果不能把每一行修改对应到根因、证据或验证需要，先缩小改动。

## 排查流程

1. 定义缺陷：
   - 现象
   - 触发条件
   - 影响范围
   - 复现路径
   - 是否稳定复现
   - 哪些旧业务路径可能受影响

2. 识别证据来源：
   - 现有日志
   - 运行时状态变化
   - 调用链或事件链
   - 网络数据
   - 本地存储或缓存状态
   - 生命周期、权限、异步取消或重入行为
   - 旧功能的历史实现和复用关系

3. 按需读取引用文件：
   - 通用排查流程：`references/investigation-flow.md`
   - 日志与临时观测点：`references/logging-playbook.md`
   - 真实设备或运行环境日志：`references/real-device-logs.md`
   - 修复方案选择：`references/fix-selection.md`
   - 验证与回归检查：`references/verification-playbook.md`

4. 编辑前说明：
   - 当前根因假设
   - 支撑它的证据
   - 问题落在哪一层
   - 最小修复边界
   - 是否仍需补证据

## 编辑规则

- 优先删除或修正错误逻辑，而不是堆叠兜底分支。
- 优先修正真实的状态源、时序、边界或契约问题。
- 不新增重复状态、重复缓存、重复请求或临时同步链路，除非根因确实要求。
- 不因为当前路径能跑就扩大修改范围。
- 临时日志在验证后移除或降噪，除非保留它有明确诊断价值。

## 决策规则

- 只有一个清晰根因和一个清晰最小修复时，直接修改。
- 多个方案涉及架构边界、接口、性能、兼容、维护成本或业务风险时，先说明选项。
- 根因仍不清楚时，不猜改；先补证据和验证路径。

检验：如果不能说清“为什么这是根因、为什么只需要这些改动、哪些路径已回归”，修复还没有闭环。

## 完成时报告

- 现象和目标
- 当前项目基线
- 根因和证据
- 差异落在哪一层
- 最小修改落在哪一层
- 改了哪些文件
- 原始问题和相邻路径如何验证
- 还有哪些未完成、未验证或待决策项
