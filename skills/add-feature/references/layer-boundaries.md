# 层级边界

当需要判断功能应该放在哪一层，以及改动应该扩散到什么范围时使用本文件。

## 归属问题

- 谁拥有业务语义？
- 谁拥有状态源？
- 谁负责生命周期、权限、缓存、网络或持久化？
- 谁是调用方，谁是被调用方？
- 这个能力是页面私有、模块内共享、跨模块共享，还是平台基础能力？

## 边界规则

- 页面级需求优先留在页面或功能层，不要直接下沉到核心层或共享层。
- 多处业务稳定复用时，再抽到明确的共享模块。
- 公共能力只暴露最小公开接口，内部实现细节不能泄漏给调用方。
- 数据、状态和事件的归属必须单一，不能让多个层互相补丁式同步。
- 跨端、跨框架、跨进程或跨服务能力，需要先定义契约，再实现适配。

## 影响面控制

- 修改公共接口前，列出所有调用方和兼容策略。
- 修改共享状态前，确认旧页面如何被动响应，避免双写和重复缓存。
- 修改存储、协议或数据结构前，确认迁移、兼容和回滚策略。
- 修改生命周期、异步回调或后台任务前，确认页面退出、重建、取消和重复触发行为。
- 修改界面或交互前，确认相邻入口、空态、异常态、加载态和可访问性。

## 避免

- 把局部需求扩散成全局改造。
- 为了复用暴露内部实现细节。
- 在多个模块维护同一份共享业务状态。
- 用临时兼容分支替代清晰边界。
