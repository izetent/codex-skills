# 功能规划

在为新增需求或扩展需求写代码前使用本文件。

## 先定义

- 需求核心：这个需求真正要解决什么问题，而不是表面上要写哪些代码。
- 用户或调用方：谁会使用它，入口在哪里，结束条件是什么。
- 成功标准：怎样算完成，哪些场景必须保持不变。
- 影响范围：页面、模块、接口、数据结构、存储、权限、平台、配置、埋点和测试。
- 约束条件：性能、兼容、生命周期、权限、安全、可访问性或发布节奏。

## 既有能力检查

- 先搜索是否已有相同功能。
- 如果已有相似功能，判断差异是业务参数、调用入口、状态归属、展示形态还是底层能力。
- 旧实现没有封装时，不默认立刻抽象。只有在边界清楚、复用点稳定、能减少真实重复时才抽离。
- 如果旧实现不稳定，先判断当前需求是否必须修正它；不要借新需求重写无关旧路径。

## 决定最窄实现路径

- 能通过配置或参数扩展解决的，不新增平行实现。
- 能在业务层编排解决的，不下沉到基础层。
- 能在局部组件解决的，不提升为全局框架。
- 需要共享的能力必须有单一真相源，不能让多个页面或模块各维护一份。

## 避免

- 需求边界不清时就改架构。
- 为一次性需求新增通用系统。
- 因为代码相似就机械抽象，忽略业务语义差异。
- 为了“以后可能会用”预留大量当前用不到的能力。
