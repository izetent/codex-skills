# 功能开发

当任务是新增功能或扩展既有功能时使用本技能。目标不是为了写代码而写代码，而是理解需求核心，选择最窄责任层，用精准修改完成业务目标，并保证不破坏既有业务路径。

## 核心规则

- 先理解需求核心：它到底为了解决什么问题，服务哪个用户路径或业务目标。
- 写代码前先拆需求、定边界、评估影响面。
- 不替用户做错误假设；存在歧义时先说明多种解释、权衡和推荐项。
- 先查现有能力：是否已经存在相同或相似功能，能否复用，是否值得抽离封装。
- 修改必须像手术刀一样精准，只改真正负责该需求的层和模块。
- 优先做精简高效的设计，不为了“通用”而过度抽象，不为了写代码而写代码。
- 新需求不能破坏旧业务。实现前识别受影响路径，实现后验证新路径和邻近旧路径。
- 如果需求会改变公共接口、共享状态、数据结构、协议、存储或跨端行为，先说明设计和取舍，再编辑。

检验：每一处新增或修改都必须能追溯到当前需求；如果解释不清它为什么属于当前需求，删除或推迟。

## Karpathy 启发的执行原则

- 编码前思考：先暴露假设、困惑和取舍，不把不确定性藏进实现。
- 简洁优先：用最少代码达成目标，不为一次性需求创建框架或配置系统。
- 精准修改：只碰当前需求必须触碰的代码，不顺手重构无关路径。
- 目标驱动：先定义成功标准和验证方式，再循环实现直到达成。

检验：如果一个资深工程师会问“为什么不直接这样做”，先简化设计再继续。

## 执行流程

1. 定义功能：
   - 业务目标
   - 用户路径或调用路径
   - 起点和终点
   - 影响的页面、模块、接口、数据或平台
   - 成功标准和不应破坏的既有路径

2. 按需读取引用文件：
   - 需求拆解与复用判断：`references/feature-planning.md`
   - 实现边界与影响面：`references/layer-boundaries.md`
   - 验证闭环：`references/feature-validation.md`

3. 编辑前说明：
   - 需求核心是什么
   - 现有能力是否已覆盖或可复用
   - 功能应该落在哪一层，为什么
   - 最小实现范围是什么
   - 需要重点保护哪些旧业务路径

## 编辑规则

- 跟随仓库已有架构、命名、状态归属、依赖注入、网络、存储和测试方式。
- 优先复用现有能力；相似逻辑重复出现并且边界稳定时，才抽离封装。
- 新增接口面必须最小、语义明确、调用方稳定。
- 状态归属必须清楚，不能让多个模块长期维护同一份业务状态。
- 不把一次性需求包装成庞大框架，不引入当前需求用不到的扩展点。
- 不用兜底分支、强制刷新、延时、重复请求掩盖设计不清或状态归属错误。
- 发现旧实现本身存在风险时，只处理和当前需求直接相关的最小部分；更大治理另行说明。

检验：改动边界必须小到可以清楚列出“改了哪些层、为什么只改这些层、哪些旧路径被保护”。

## 完成时报告

- 目标和需求核心
- 当前项目基线和已有能力
- 差异落在哪一层
- 最小修改落在哪一层
- 改了哪些文件
- 验证了新路径和哪些旧路径
- 还有哪些未完成、未验证或待决策项
